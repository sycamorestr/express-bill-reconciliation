# 稳定执行与复现规则

适用版本：**1.1.0**。目标是让不同使用者在相同输入文件、实际配置与引擎版本下得到相同运单集合、金额、主原因和待核项。对结果的解释与排版可以不同，计算口径不能由模型临时决定。

## 当前实现的范围

- 输入为三个独立 `.xlsx` 文件。账单按配置选择唯一工作表和表头；有多个候选时必须指定，不能默认首张工作表。需要合并多份账单时先定义合并和重复处理方案，不能直接按本模式猜合并。
- 检查账期、承运商和业务主体；当前引擎处理所选账单页的全部明细，不自动按月份或承运商过滤。选择范围应在配置及报告中说明，范围不明时单号差集只能称“仅某账单存在”，不能直接称漏单。合计、小计和明确空白行的排除要保留来源依据。
- 默认 `carrier_policy=yuantong_brand_aliases`：承运商原名须完整匹配“圆通速递”或“圆通快递”，可带支持的网点前缀及 `_数字` 后缀。同品牌的多个网点名称仅归并为“圆通”用于范围校验，全部原名保留在 `input_metadata.system.carrier_values`，归并品牌及策略分别保留在 `carrier_brand`、`carrier_policy`。不匹配的品牌会报错，不能因价格表外形相同就擅自同价核对；未提供承运商字段也不能据此证明双方同品牌或同主体。
- 价格模式仅为 `dated_matrix_v1`：一个所选价格工作表内，按生效日期标题分块，各块为地区行与重量档列的数字整票价。实际金额来自输入价格表，profile 不带历史报价。
- 报价中的通用首续重、体积重、最低收费、复杂附加费、任意公式以及其他未实现报价模式均不自动执行。遇到这类条款，记录待核依据及影响范围；不能以增加一段自然语言配置代替受测试的计算实现。
- 快递收费可读取明确数值，或重算已映射费用列的**本行两项加法**。其他公式即使有缓存，也不自动当作已可靠核定；保留待核。价格表中的公式价格同样不能只凭缓存宣称可靠。
- 重量单位固定 kg，币种人民币，金额采用 Decimal、分精度、`ROUND_HALF_UP`。其他单位或舍入合同不在此版本的可直接切换范围内，需增加明确支持并验证后发布新引擎版本。
- 已支持布局中的单票缺失、疑点只阻断依赖该资料的检查，其他独立核对继续。无法唯一选表、无法识别整体结构、配置不受支持或输入损坏时，命令失败并说明原因；不能输出“全部一致”。

以下详细业务规则是检查依据。当前引擎未实现的报价类型应待核，不表示可以临时另写算法完成核价。

## 配置与版本

以 `profiles/yuantong-jushuitan-v1.json` 为完整模板；自定义时复制该文件，保留必需键，再修改受支持项。使用 UTF-8 JSON，不添加未知键、不依赖注释、不放入系统原运费映射。字段别名、工作表等受支持配置变更必须更新 `config_revision` 并保存配置 SHA256；默认修订号为字符串 `"1"`，新修订可使用其他非空文本。`profile_version` 固定为 `"1.1.0"`、`profile_id` 固定为 `"yuantong-jushuitan-v1"`，二者标识兼容算法，不能为了区分文件或场景而修改。修订号只记录配置变更，不能让算法自动支持新规则。

| 配置项 | 本版本含义 |
|---|---|
| `profile_id`、`profile_version` | 固定为 `yuantong-jushuitan-v1`、`1.1.0`，用于验证算法兼容性，不是用户自定义修订号 |
| `config_revision` | 用户配置修订号，默认 `"1"`，必须为非空文本；修改受支持映射后更新，随结果、有效配置和 manifest 保存 |
| `sheets.courier/system/price` | 显式工作表名；`null` 表示按受支持结构寻找唯一候选 |
| `header_rows.courier/system` | 显式账单表头行；`null` 表示按搜索范围寻找唯一候选 |
| `header_search_rows` | 账单表头搜索范围，默认前 30 行 |
| `aliases.courier`、`aliases.system` | 字段到表头别名的映射；多个列同时匹配时必须收窄配置，不任选一列 |
| `aliases.price_region` | 报价地区列表头别名 |
| `summary_labels` | 明确的合计、小计等标签，不参与逐单匹配或累计 |
| `city_exceptions` | 本版本固定为 `{"广东": ["深圳"]}`；不支持任意新增城市专价，不能为凑价而修改 |
| `carrier_policy` | 固定为 `yuantong_brand_aliases`；按圆通品牌完整名称模式识别，归并用于范围校验，全部原名保留 |
| `price_mode`、`currency`、`rounding`、`weight_unit` | 固定为默认配置声明的受支持模式、币种、舍入与单位 |
| `date_policy`、`region_policy`、`duplicate_policy`、`formula_mode`、`boundary_policy` | 本版本已实现的固定策略标识，不能用未经实现的字符串改变算法 |

用户明确修订合同口径时，先判断当前配置能力能否表达。能表达的变更写入 profile、更新 `config_revision` 并重跑；不能表达的，补齐引擎实现及覆盖新规则的测试、更新引擎版本后再算，不能只修改固定 policy 字符串或兼容版本号。未明确的日期、地区、边界或首续重条件继续待核。不能以静默修改价格表、手改结果或暂存聊天记忆实现规则变更。

`profile-resolved.json` 是本次传给引擎的完整有效配置副本；字段最终命中的工作表、表头及列位置还需随结果保留。复现使用该配置副本，不取后来修改过的默认 profile。引擎固定版本取 Git 标签 `v1.1.0`，不能把持续更新的主分支当作同一版本。

## 权威结果与展示

`result.json` 是唯一核算结果。它包含版本、汇总、异常明细、完整逐单记录、商品汇总、举证集合、价格规则、规则疑点及验证信息；金额与重量以十进制字符串保存，未知值为 `null`。原始输入、配置、代码、结果及导出文件的 SHA256 和运行环境由 `manifest.json` 记录。

- 工作簿只能呈现机器结果。内部首页、运单明细、原因分类、举证名单、所有摘要单量与金额均取机器结果，不在渲染时重新核价或归因。
- 可以临时编写排版及原工作表复制脚本，但只允许读取已有结果来填值、设置样式、筛选及跳转。不得在展示层实现另一套业务逻辑、按说明文字猜主原因，或用 Excel 公式重新计算运费。
- 金额从十进制字符串写成 Excel 数值，单号和商品编码按文本写入；空金额保持空白。表内可显示格式化到分的数值，完整精度仍以 JSON 为准。
- CSV 是查阅和交换副本。用 Excel 导入时将单号、商品编码设为文本，避免长单号或前导零损坏；CSV 可能对公式样式文本加保护前缀，不能据此修改原始标识。JSON 中的标识才是权威值。
- 原快递页、完整价表和完整系统页的复制、公式保真及源行跳转仍遵循 [output-contract.md](output-contract.md)。系统原运费只允许原件保留，不参与任何核算。
- 排版无法完成时，应如实交付已完成的机器结果并说明缺少的工作簿，不把 CSV 冒充已完成的 Excel 举证表。

## 固定判断优先级

无法识别的空单号、损坏精度或公式单号先列待补单号记录，不捏造运单进入单量。对可识别运单依次采用第一个适用主原因；独立检查发现作为附加事实保留，不重复计入分类。

| 优先级 | 主原因 |
|---|---|
| 1 | 关联待核实：重复或商品多行等无法唯一关联 |
| 2 | 仅快递有单 |
| 3 | 仅系统有单 |
| 4 | 地区和日期待确认：地区与日期均阻断核价，合为一个主原因 |
| 5 | 地区待确认：冲突、不足或无法唯一选择计价地区 |
| 6 | 日期待确认：双方跨版本且口径不明确 |
| 7 | 报价规则待确认，或缺重量/收费等资料待补；具体阻断依据必须保留 |
| 8 | 重量影响运费：重量影响非零，计价差异为零 |
| 9 | 计价不符：重量影响为零，计价差异非零 |
| 10 | 重量＋计价差异：两个分解项均非零，包含相互抵消为零的情况 |
| 11 | 跨档但运费不变：两个分解项均为零，但比较档或实际计价档改变 |

前七类不能被后面的已知差额覆盖；未知金额不是零。“地区和日期待确认”仍每票只计一次，两个具体疑点均保留在附加事实中，不再重复计入纯地区或纯日期类别。两个分解项均为零且同档计价不变则正常，重量小差计入已忽略数量。原因标签、商品汇总、举证范围均由引擎决定；不得另加“收费不符”一类重复统计。

大于 3kg 的重量恰好处于两个相邻报价档的共同端点时，如果两档均有明确数字且舍入后金额相同，可以保留唯一的 C/S 参考金额及可确定的辅助差额，并保留两个候选价表单元格。此时边界开闭规则仍不明确，主原因优先为“报价规则待确认”，不能归为已经确定的重量影响或计价不符，也不能进入快递举证。两档异价、不是相邻档或存在其他阻断依据时不能取其中一价。金额唯一不等于报价规则完全确定。

完整金额解释、仓库/快递核查路径和举证筛选见 [output-contract.md](output-contract.md)。快递举证必须取 `result.json` 的举证集合，只有依据完整且总差额为正的运单；跨运单少收不得抵扣多收。

## 复现检查与失败处理

1. 保留原三份文件、文件名、工作表和行次，保留该次 `profile-resolved.json`、`manifest.json`、`result.json`，以及同一引擎版本。运行时输入不能被其他进程修改。
2. 依赖固定为 `openpyxl==3.1.5`，Python 3.10+。运行 `python -m unittest discover -s tests -v` 做引擎自检；单次任务还必须通过结果自身的守恒及完整性验证。
3. 对照 manifest 中的输入、配置和代码 SHA256。完全一致后，复现运行使用新的空输出目录，并加入 `--compare`：

   ```sh
   python -X utf8 scripts/reconcile.py --courier "快递公司账单.xlsx" --system "聚水潭系统账单.xlsx" --price "价格表.xlsx" --profile "outputs/run-001/profile-resolved.json" --output-dir "outputs/run-002" --compare "outputs/run-001/result.json"
   ```

4. `--compare` 对完整规范化 JSON 比较；成功记录比对结果。不一致时退出码为 `2`，不交付新一轮结果文件；先找出输入、源定位、配置或引擎变更，不修改旧结果来使比对通过。未指定 `--compare` 不等于已通过复现比对。
5. 任一输入不受支持、输出目录非空、依赖版本不符或验证失败时，按实际错误修正后使用新目录重跑。受影响单票“待核”属于有效核对结果，不等于整次引擎失败；交付时必须保留待核单量和缺口。

结果比较涵盖逐单匹配、重量档、核价状态、各金额、主原因、商品汇总、举证集合、规则疑点及源依据。`result.json` 不含运行时间；manifest 的环境信息、输出文件时间及 Excel ZIP 容器元数据可不同。不得承诺跨引擎版本、跨配置或未经支持的新报价模式结果仍然相同。

## 1. 快递单号是否一致

- 单号按文本比较，去除首尾空白；保留前导零、字母和内部字符，不做模糊匹配。数值单号超过 Excel 15 位精度、已损坏的科学计数法或异常小数标“单号精度待核实”，不能猜测还原。
- 做双向匹配：快递有且系统有、仅快递有、仅系统有；另列空单号、重复单号。快递侧匹配成功写“已匹配”；无对应记录写“未匹配”。
- 同单号多行不能取第一行、覆盖映射或重复累加运费/包裹重量。先区分商品明细拆行、重复账单、退回/补收等业务。当前 `duplicate_policy=pending_no_aggregation` 对重复关联保留待核，暂停该运单依赖一对一关联的检查；即使补齐业务证据，也需将明确的聚合方式纳入后续受测试的引擎版本才能自动汇总，不能在展示层合并重算。
- 汇总分别注明记录行数、去重单号数及匹配统计口径。保留来源工作表和行号。

## 2. 重量是否一致

同时给出原始重量比较和重量区间比较。两者不得共用一个模糊的“一致”结论。

- 统一为 kg，原始值另存；空值、非数值、负数分别标明原因，不替换为 0。原规则包含 0，不能自行删掉 0kg 档。
- `重量差异kg = 快递重量 − 系统重量`，正数表示快递记录更重。用十进制值比较，默认不添加业务容差；用户另定容差时记录。
- 两份账单各自按以下用户规则分档，再按单号把系统区间回填到快递主表。

| 重量 kg（用户原文） | 区间名称 |
|---|---|
| 0–0.3 | 0.3kg重量 |
| 0.301–0.5 | 0.5kg重量 |
| 0.501–1 | 1kg重量 |
| 1.001–2 | 2kg重量 |
| 2.001–3 | 3kg重量 |
| 大于3 | 3kg以上重量 |

- 上述区间在三位小数精度下连续。遇到 `0.3005`、`0.5005` 等落入文字间隙的值，标“重量边界待确认”，不要先四舍五入，也不要静默改成连续开闭区间。仅澄清受影响规则，其他运单继续。
- 区间比较状态为“一致 / 不一致 / 未匹配 / 数据异常或待确认”。同为“3kg以上重量”仅表示粗区间相同，仍需比较价格表实际细分列；两边命中同一实际价格表重量列且计算金额不变时，原始重量差异按用户规则忽略。若地区、日期或价格规则待确认，不能把该重量差直接判定为不影响计价，应保留在对应待核价原因中。
- 所有纳入商品异常汇总的运单均关联系统商品编码和商品件数，不限于重量区间不一致的运单。完整商品编码作为分组键，中文、组合装和 `*` 保留原内容，不自动拆成单品或按件数重复分摊整票运费。编码缺失、件数缺失分别记录；快递独有且无法关联商品的运单单独归组。多商品/多行须保持编码与数量对应，未解决的一对多关联列待核实，不能无依据拆分数量或重复累计运单和金额。

## 3. 价格表规则及选用是否正确

用户确认的范围为：**检查价格表自身规则，并核对账单是否用对价格表**。这里不代表与合同报价比对或证明双方已认可该报价。

先审核规则，再用可确定的规则核价：

- 读取版本标题、生效起止日期、地区行、重量列、单价/整票价/首续重价、附加费和备注，形成带源单元格的“价格规则”清单。合并单元格只在真实覆盖范围内展开，不跨表头/版本盲目前填。
- 检查日期重叠/缺口，地区漏配/冲突，重量边界重叠/缺口，空白、非数值、负值、公式错误、缺失计算值及单位不明。零价或重量增大但价格下降只标“疑点”，不能凭常识改价。检查范围以本次账单覆盖与价格表声明为依据，不凭空要求全国地区都有价。
- 日期段只有月日无年份时，可在账单只有一个明确年度且月份吻合时补足年份并标注来源；多年度、跨月或字段歧义需确认。每票记录所用计费日期及来源。默认用快递账单“日期”选版本并记录此口径；用户/价格表规定发货日、揽收日或结算日时遵循规定。双方日期跨版本且口径不明时受影响记录待确认，不能挑选更接近账单金额的日期。
- 地区匹配遵循价格表明确的城市/区县例外优先于省级通用价。解析完整行政区划，避免把“甘肃省兰州市黄河北”当成河北省。快递地址无法识别时，可由唯一匹配的系统省市区补足，并标“地区来源=系统补足”；两边明确冲突时保留两者，标“地区冲突待核实”。
- 重量计价档以价格表原文为准，与六档重量分类分开保存。不能把所有 >3kg 按3kg、把列名“30kg”擅自扩展为“25–30kg”，或凭“首重【金额】元，加收【金额】元/kg”猜首重公斤数和续重进位方式。>3kg 相邻档共同端点仅在两档金额明确且相同时保留唯一金额；边界待核及两个候选依据必须保留，不能因此宣称规则已唯一明确。
- 注明附加费条件、金额单位、是否已含在基础价中及是否每票只加一次。地区独立报价本身不是另收附加费的依据。条件或叠加关系不明则待确认，不补 0 或重复加收。
- 每票可用价格规则应唯一：0 条为“缺少规则”，多条为“规则冲突”。明确的特殊地区覆盖关系可以解决通用规则重叠，其余情况不能取首条或最低价。
- 账单通常没有直接记录价格版本。此时只验证“本次应选的规则及金额是否一致”；金额碰巧等于旧版价格可作为线索，不能据此断言快递公司实际用了该旧版。
- 保留原价表及疑点影响范围，不自动改价。具体报告“未发现已检查范围内的规则问题”“发现疑点”或“无法判断”，不能笼统声称价格表绝对正确。

## 4. 价格是否一致

承接用户先按快递重量、再按系统重量区间核价的要求，默认同时保留两套计算：

1. **按快递重量计算**：用快递原始重量匹配用户价格表的实际计费规则，重新计算运费。
2. **按系统重量计算**：使用系统实际重量匹配用户价格表，独立计算运费。示例中≤3kg 可对应六档整档报价；>3kg 仍按实际重量进入明确的细分/续重规则。重量比较六档与价格表档位不同时，以实际重量匹配价格表计价，保留两种档位及计算依据。不能用六档区间上限替代实际重量，或取更优惠的档位。

输出统一使用三个列名：**快递账单收费**（快递公司实际账单运费）、**按快递重量计算**、**按系统重量计算**。后两列是核对参考值，不表示已经确认的最终应付金额；系统计算列也不是聚水潭原运费。源文件字段名称保持原样。

两套计算使用同一已确定的日期和地区口径，仅改变重量依据。**不得读取聚水潭“运费”作为任一核价依据，也不做快递运费与聚水潭原运费直接比较。**

- 优先读取快递账单“运费”的数值；公式单元格同时检查表达式和缓存，缺失缓存不能当作 0。示例快递运费为“差额+充单”，仅在公式和依赖都确认后可重算，保留计算来源。复杂公式当前不支持，标“运费无法确定”；不能执行任意公式字符串作为代码或临时另写计算器。
- `计算运费 = 按明确规则计算的基础运费 + 适用附加费`，报价已含加收时不重复叠加。首续重、进位、最低收费、取整顺序以本次价格表或确认规则为准。
- 总差额为 `快递账单收费 − 按系统重量计算`。在相同已确定日期、地区与价格规则下分解为：`重量影响金额 = 按快递重量计算 − 按系统重量计算`；`计价差异金额 = 快递账单收费 − 按快递重量计算`；两项之和必须等于总差额。正负均保留，不能把差额认定为可追回款。默认人民币分、十进制 ROUND_HALF_UP 比较最终金额，价表另有规则时覆盖；保留中间精度并记录舍入规则。
- 报告应隐藏“同一比较区间且计价不变”的原始重量差明细，只在汇总说明忽略数量。跨比较区间的记录继续列出，即使相邻报价恰好相同，也标记为“区间变化但本次金额未变”；价格未确定的记录进入待核价明细。
- 运费核对状态为“一致 / 差异 / 未核价（具体原因）”。缺单、无重量、规则不明等不能变成一致，也不能混入已核价差异总计。
- 四项检查相互独立：快递侧未匹配系统单号，但自身日期、地区、重量、金额及规则完整时，仍可按快递重量核价；系统重量核价及重量比对保持未匹配。系统同号多行也只暂停依赖该关联的检查，快递自身数据明确时仍独立核价。重量比较分档待确认、但实际重量在价格表上有独立明确计价依据时，也可继续核价并说明。不能让一项疑点屏蔽不依赖它的其他检查。
